About Alkansya

Alkansya is a web application designed to empower Filipino students and young adults in their financial journeys. Inspired by the traditional Filipino piggy bank, Alkansya transforms saving from a daunting task into a motivating and rewarding experience. Instead of just tracking expenses, it focuses on connecting every peso saved to tangible dreams and aspirations.

🎯 Project Objectives

  • User-Friendly Platform: Provide an intuitive interface for creating, tracking, and managing multiple savings goals
  • Mindset Transformation: Shift saving from a restrictive chore to an exciting path towards personal dreams
  • Motivation Enhancement: Foster engagement through visual progress tracking and milestone celebrations
  • Financial Insights: Offer clear analytics to help users understand their saving habits

Firebase Setup

1. Create Firebase Project

  1. Go to Firebase Console
  2. Click "Add project" and follow the setup steps

2. Enable Firebase Services

Authentication

  • Navigate to Build > Authentication > Sign-in method
  • Enable Email/Password authentication

Firestore Database

  • Go to Build > Firestore Database
  • Start in production mode
  • Choose your preferred location

Cloud Messaging

  • Navigate to Engage > Messaging > Cloud Messaging
  • Generate Web Push certificates (VAPID key)

Analytics

  • Go to Engage > Analytics > Dashboard
  • Enable Analytics

3. Get Configuration

  1. In Firebase project settings, add a new Web app
  2. Copy your firebaseConfig object
  3. Create .env.local file in project root:
VITE_FIREBASE_API_KEY="your_api_key"
VITE_FIREBASE_AUTH_DOMAIN="your_auth_domain"  
VITE_FIREBASE_PROJECT_ID="your_project_id"
VITE_FIREBASE_STORAGE_BUCKET="your_storage_bucket"
VITE_FIREBASE_MESSAGING_SENDER_ID="your_sender_id"
VITE_FIREBASE_APP_ID="your_app_id"
VITE_FIREBASE_MEASUREMENT_ID="your_measurement_id"
VITE_FIREBASE_VAPID_KEY="your_vapid_key"

⚠️ Important: Ensure .env.local is in your .gitignore

Firebase Security Rules

Firestore Rules

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    
    // Goals collection rules
    match /goals/{goalId} {
      // Users can only access their own goals
      allow read, update, delete: if request.auth.uid == resource.data.userId;
      allow create: if request.auth.uid == request.resource.data.userId;

      // Contributions subcollection rules  
      match /contributions/{contributionId} {
        // Users can only access contributions for their own goals
        allow read, create: if request.auth.uid == 
          get(/databases/$(database)/documents/goals/$(goalId)).data.userId;
      }
    }
    
    // Users collection rules
    match /users/{userId} {
      // Users can only access their own user document
      allow read, write: if request.auth.uid == userId;
    }
  }
}

Storage Rules

rules_version = '2';
service firebase.storage {
  match /b/{bucket}/o {
    match /images/{userId}/{fileName} {
      allow read;  // Public read access for images
      allow write: if request.auth != null && 
                   request.resource.size < 5 * 1024 * 1024; // 5MB limit
    }
  }
}

Challenges & Solutions

🎨 UI Library Configuration Conflicts

Problem: Initial attempts with Tailwind CSS and Chakra UI led to build errors and dependency conflicts with Vite.

Solution: Switched to plain CSS with custom modular stylesheets. This eliminated all build errors and provided complete control over styling.

🔑 API Key Exposure Prevention

Problem: Firebase Cloud Messaging service worker required hardcoded API keys, risking exposure in Git history.

Solution: Created a Node.js build script that dynamically injects API keys from .env.local into the service worker at build time, keeping keys out of version control.

📅 Date-Based Calculation Accuracy

Problem: "Savings per week" calculations were producing incorrect results due to time-of-day differences and rounding errors.

Solution: Rewrote calculation logic to use whole calendar days and implemented adaptive display (per week/day/total needed) based on deadline urgency.

🛡️ Firestore Security & Permissions

Problem: Complex permission errors with subcollections and race conditions during database seeding.

Solution:

  • Restructured Firestore Security Rules with nested match blocks
  • Used get() function to link subcollection permissions to parent documents
  • Implemented two-phase commit with writeBatch and onAuthStateChanged for seeding
